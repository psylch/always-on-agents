Raft：快速回复、纠偏与长期协作的代码级研究

Raft 让有身份、记忆和目录的 agent 成为队友，用协作状态与 daemon 管运行。“先回一句”靠提示词和显式发送，未见快模型或确认检查器。新消息经 inbox 与 steer 注入，不自动取消工具；Stop 有 abort 路径，但结果补齐、副作用和 helper 存活无统一保证。租约与 fencing 已实现，通用 durable-task registry 却为空且默认关闭。增量是任务所有权、发送前新鲜度检查、按 launch 绑定的凭据代理与“不确定则不重跑”的故障语义。OAR、antiproton、K 是独立组件，接入须核实；投资看完成与恢复，复用须区分 FSL 和组件许可。

8．相对 Grok Bot 真正的新意，与 Charles 应盯的指标

【判断】Raft 更有辨识度的部分是团队协作状态与运行来源的可核验性。 Grok 课程描述单用户 main Bot＋helper、统一 conversation 和云电脑；Raft 代码中命名 agent 是 peer，有各自机器/session/workspace，通过 channel/thread/task协作。claim 的规范所有权、write 前 freshness hold、notification与model-seen分离、runtime binding fence和 outcome-unreliable 状态，比“给 agent 接聊天软件”更接近真实团队的并发与责任问题。它们在上文都有具体控制流，但本研究无法据此证明 Raft 长任务完成率高于 Grok；闭源参照没有等价测试数据。Grok 来源：课程讲义（课程：75–87）、课程讲义（130–133）。

Raft 还把多 provider 控制/观测、cloud durable运行、终端升级、凭据脱敏等需求拆成独立组件，能支持更宽的开发者生态；从投资角度，这是分发与基础设施复用的潜力，而不是已经形成收入或网络效应的证据。关键尽调轨迹应是同一请求贯穿：确认已提交→两个 agent竞争认领→执行中用户改目标→远端 API可能已成功但响应丢失→runtime进程死亡→helper晚回→摘要/冷启动→再次读取正确任务状态。量必要确认 P50/P95、纠偏生效时延、重复副作用、错误成功宣告、人工恢复率、权限撤销后拒绝率、每完成任务总成本。要把“实现已有”“feature flag打开”“目标用户实际使用”“指标改善”四层逐级给证据。

快回复、共享文件记忆、helper分工、通知只承载变化和provider cache前缀都不是本研究可宣布的 Raft独创；Grok课程已经描述这些方向。真正可投资的增量应在跨机器和多agent协作的有效完成率、故障边界及持续改进数据。未找到 Raft主agent专用训练、SFT/RL配方、独立长期 benchmark、规模化生产恢复率的证据；课程对 Grok训练的说明也只是厂商自述。课程讲义（课程：148–174、178–186）。
