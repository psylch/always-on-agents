Always-on agent 的十一层机制：从 Grok Bot 到可核验的实现

研究截点：2026-10-11。核心判断：always-on 正在收敛为“事件驱动、持久状态、外置工具环境、可压缩上下文与按需 skills”，但十一层机制远未同构：触发上 Grok 按人/后台分流，OpenClaw、Hermes 提供不同 steering/排队语义；运行时上 Grok 分离 server loop 与 Firecracker 电脑，Muse 围绕个人 VM 保存权威状态，本地 harness 则把在线性留给部署者；恢复上 Temporal replay、Raft 事务任务与 OpenHands 事件日志各解决不同故障；说话上 Grok 专用 send，Hermes/OpenClaw 可交付普通回复并抑制沉默；工具上 Codex deferred schema、Goose 动态扩展、Manus decoding mask 分叉；电脑使用上结构索引、像素与人接管互补；多 agent 已有隔离会话，但取消和共享资源所有权仍难；上下文正收敛到稳定前缀与可重读文件，摘要时机未统一；记忆从小档案、Letta 分层 MemFS 到 Codex 后台 consolidation；安全从 callback/审核模型发展到独立出口授权；评测已有故障回归，和模型训练闭环之间仍缺公开证据。对产品与投资，稀缺能力是可验证的恢复、授权、纠偏与长期完成率，而不是多几个入口、VM 或 helper。下文逐章给出这些判断的依据。

证据口径：讲座自述来自用户提供的 lecture-slides.md，讲于 2026-10-08、记录标注发布于 10-09；未重新核验视频逐字稿。源码观察是对固定 Git 提交的独立静态审阅，不代表运行验证或第三方安全审计；README、工程博客、产品文档始终视为厂商/维护者自述。文中“取舍”是研究判断。正文按有证据的机制比较，未公开的闭源实现不靠推断补齐；仓库 URL、星数和 HEAD 日期见文末；代码链接固定到本次提交，另有逐项引用索引。

1. 唤醒与触发：把“来了什么”与“现在做什么”分开

【讲座】Grok Bot 的消息、routine/webhook、Slack、电话、helper 完成事件先进入 router：去重、确定 conversation，再放入每会话串行队列。唤醒记录来源；1:1 用户消息可以插队、中断正在进行的 turn，群聊、routine 和 helper 结果则批处理。这意味着“用户纠偏”是调度优先级，而不只是追加一条 prompt。（讲座：lecture-slides.md:61–65、100–103。）

【源码】OpenClaw 把策略做成配置。src/auto-reply/reply/queue/settings.ts:14–44 的优先级是当次参数、session 配置、channel 配置、全局配置，最后默认 steer；因此不能照搬早期文档说它一律 collect。src/auto-reply/reply/queue/enqueue.ts:42–102 的去重键同时包含 queue、channel/to/account/thread、chat type 和 message ID，用 JSON tuple 避免分隔符碰撞；缺少 message ID 的消息不受这条去重保护。src/auto-reply/reply/queue/enqueue.ts:104–170,314–385 还把尚未决定能否注入当前 turn 的 steer 留在队列，失败再回退，避免纠偏请求与后续 FIFO 消息乱序。它并非硬编码“私聊必打断”，而是可按入口选择调度语义。

heartbeat 也不能简单理解成 cron 别名。当前 src/infra/heartbeat-wake.ts:12–25 将旧 SDK 接口映射到 session-event wake，并区分请求在途、cron 正在运行、无待处理事件、被抢占等跳过原因。仓库文档 docs/gateway/heartbeat.md:25–29,94–100 明确：every: "0m" 只关闭周期 poll，后台 exec 完成仍可唤醒；完成事件返回工作所属 session，周期 poll 默认进入主 session；两者带不同来源标记。cron 的 src/cron/service/timer-execution.ts:66–104 则校验 stream schedule key 与 source identity，在异步触发器结束后再次检查 abort，防止已取消的旧来源继续执行。这是“来源”参与正确性判断的实例，而不只是日志装饰。

【源码】Hermes 的消息平台 gateway 与桌面 Bot Mode 要分开看，后者另有 tui_gateway 和 Bot Chat 同事通信（第四、七章）。消息入口 gateway/run_inbound.py:693–744 默认 interrupt，支持 queue、steer，但活跃子 agent 或正在压缩上下文时强制降级排队：前者避免打断级联取消正在运行的 delegate，后者避免压缩轮换 session ID 时生成孤立分支。652–691 对纯文本尝试 steer/redirect，媒体则进入中断路径；Telegram 连续图片也有单独缓冲（616–645）。这比“支持打断”四个字有用：真正的产品延迟由可安全中断的位置决定。

Codex 也已有具体事件通道。codex-rs/app-server/src/request_processors/mcp_event_stream.rs:29–105 将 MCP subscription 限于 hosted apps，拒绝重复 subscription_id，限制单连接订阅数，并要求连接已订阅目标 thread；启动中身份发生变化会失败。重连上限为三次、间隔一秒、启动超时九十秒。这是带身份约束的事件入口，不能据此声称所有终端 CLI session 已永久托管。Goose 的 crates/goose/src/scheduler/full.rs:30–31,75–100 则将定时 recipe 列表存为 JSON，以 Tokio scheduler 驱动，运行中任务和取消 token 在内存。保存“下次何时运行”和保存“这次执行到哪”是不同的数据结构。

【源码】社区 DS Bot 的 ds-bot/src/host/schedules.js:1–7,71–117 注入 Harness 的可选 schedule service，将到期 prompt 投递至 Bot 或群组自己的 DSH Session；automation bundle 未开启就返回 unavailable。16–28 把 reminder JSON 转成 [Scheduled task] 来源文本。127–140 开始处理换新 session 后的 schedule 迁移，因此持久身份不能只靠延长单个上下文。其 README:98 明确不是 DeepSeek 官方产品；不要与官方 deepseek-ai/deepseek-harness 合并计算产品能力。

【官方】Claude Code Channels 是向运行中的 session 推送 MCP 事件；Routines 是托管的 prompt、repo、环境和触发器组合，可从 schedule、API、GitHub 事件启动。两者解决的生命周期不同。Cowork 当前定时任务说明称任务远程执行、每次独立 session，但依赖本地文件/app 的任务仍在本地，且 Pro/Max 在 10 月 6 日前创建的本地任务保留旧行为（访问 2026-10-11）。Muse 的产品设计文描述事件与日程推进工作、用户可插话，却未公开具体 queue 和去重实现。dots 的发布材料也不足以核实 router；不应由“全天在线”反推这些细节。

【判断】这里已收敛的是把事件送给有身份的会话，仍分叉的是纠偏怎样进入执行流。产品验收应测“同一 webhook 重发三次只创建一次工作”“连续发三条纠正后最终按哪个版本执行”“压缩或 helper 工作时停止多久生效”。把所有事件拼进一个 prompt，无法代替这个调度层。

2. 运行时与云电脑：agent 进程和工具电脑有两个生命周期

【讲座】Grok Bot 在 server 跑 loop 与保存状态，空闲两分钟后 agent 进程停止；每用户一台 Firecracker VM，内部 Debian container、supervisor、文件服务和命令服务，每个活跃 agent 有独立 Chrome/虚拟屏幕。电脑闲置后 sync files→snapshot→stop，下次工具调用才恢复，不能在 turn 中途休眠。会话真相留在服务器，VM 可重建。这一分离同时降低闲置算力和客户端依赖；“always-on”指可唤醒与状态连续，并不意味着 CPU 常开。（讲座：lecture-slides.md:57–87。）

【源码】E2B 提供的是工具执行环境，不能替应用保存“用户刚刚取消了什么”。其 infra 已重定向到 e2b-dev/runtime。packages/api/internal/orchestrator/pause_instance.go:29–80 先创建 snapshot build，再调用节点 Pause，只有成功才更新快照类型；节点容量不足会标记 build 失败并返回可重试的 PauseQueueExhaustedError。85–113 传递 FilesystemOnly，说明只保存文件系统与保存进程内存是不同恢复契约。Firecracker 自己的 docs/snapshotting/snapshot-support.md:56–99 明确快照包含 guest memory 与虚拟硬件状态，磁盘文件由使用者管理；恢复不能保证原网络连接存活，快照生命周期、鉴权和加密也交给上层。故“浏览器登录还在”可以来自持久 cookie，不能推出 WebSocket、下载和支付请求继续精确运行。

【源码与官方文档】隔离层有三条路线：普通 Docker 使用宿主内核；gVisor 以用户态 application kernel 实现 Linux 接口，其 OCI runtime runsc 可接 Docker/Kubernetes；Firecracker 保存一个微型 VM 的 guest 状态。gVisor README:10–45 明确自己不是 syscall filter，也不是传统 VM；其 pkg/sentry/kernel/task_syscall.go:84–146 在 sentry 内查 syscall table，经过 tracing/security hook 后调用自己的 syscall 实现，而非简单把所有 guest syscall 原样放行。Firecracker 的 src/vmm/src/persist.rs:168–199 则先保存 VMM state，再通过 KVM 将 guest memory 写入独立文件，最后重新标记 virtio queue 的 dirty memory。容器镜像解决打包，gVisor/VM 解决隔离，调度器与外部存储解决何时停、停后丢什么；不能把 Docker、gVisor、Firecracker 当成三个同层互斥选项。

Daytona 的版本边界尤其需要说清：本地默认分支 HEAD 是 2026-06-25 的文档树，以下读的是同仓库 2026-06-23 提交 01c502bb1f1ff8f2885d0cd490e043736083dca8 的源码摘录，不宣称它就是十月托管服务的部署版本。apps/api/src/sandbox/managers/sandbox.manager.ts:100–169 先用 Redis 锁选一个 auto-stop worker，筛选 actual/desired 都为 STARTED、没有 pending 变更且超过闲置阈值的 sandbox，再取得单 sandbox 锁：ephemeral 实例走软删除，其余改 desiredState 为 STOPPED，交状态同步器执行；173–210 另处理已停止实例的 archive。apps/api/src/sandbox/services/sandbox-activity.service.ts:41–75 先把 last activity 放 Redis sorted set，每十秒批量刷数据库。由此可见“闲置”本身是带刷新延迟的分布式状态；不能只在模型 turn 结束时随手关闭 VM。

Hermes 已有 tools/environments/local.py、docker.py、ssh.py、modal.py、daytona.py 等执行后端；tools/environments/docker.py:53–85 会验证、去重转发的环境变量名。gateway 放在哪里与命令跑在哪里可以不同，但不能据此断言它自带 Grok 式整机快照控制面。OpenHands 当前仓库已是 Agent Canvas，README:148–168 指向另一个 OpenHands/software-agent-sdk 中的 Agent Server；README:52–66 明确可在本地或云服务器运行，无 sandbox 模式会直接暴露所在机器文件系统。Raft 的 packages/computer/ 则围绕已连接机器的 resident service、supervisor 与会话运行环境组织，属于让 agent 使用现有机器的路线；没有证据说明其一律用 Firecracker。

【官方】Muse 的安全工程说明比产品页更细：runtime cell、credential store 与保存持久应用状态的 Postgres 分隔；所以“都在用户 VM 内”也不是“都在一个 agent 容器里”。安全工程文还明确 Confidential VM 是未来能力，当前不能保证 Meta 无法访问数据。dots 的2026-09-29 发布文确认使用自己的云电脑和长时间后台工作，未公开 hypervisor、休眠阈值或工作流引擎。Manus 2.0/Cue 的官方发布入口列出共享的 Cascade harness、Cloud Computer 与 Automations；本次没有取得足够证据将其归入某一具体 VM 实现。

【判断】云电脑最有价值的指标不是“启动快”，而是活跃分钟成本、恢复后任务成功率、跨版本恢复兼容性与隔离边界。应用要把任务状态从机器状态中抽离；基础设施供应商若只卖容器创建 API，价值容易被替换，若能处理冷启动、恢复一致性和凭据边界，才承担了长期 agent 的难点。

3. 持久化与可靠性：恢复会话、恢复步骤、避免重复副作用是三件事

【讲座】Grok Bot 给消息唯一 ID，服务端拒绝重复 ID；会话队列一次执行一个 turn，每一步存储。客户端通知只表示“有变化”，真正内容从数据库拉取，以 sequence number 检查缺口。讲座用 Temporal 解释 durable workflow：崩溃后接续完成点，而普通 job queue 重跑 job。这里应补一句技术边界：job queue 也能人为拆步骤或做 checkpoint；durable workflow 也不会自动让外部发送和扣款 exactly-once。（讲座：lecture-slides.md:89–98。）

【源码】Temporal 的 openai_agents/basic/workflows/tools_workflow.py:13–28 把 Runner.run 放进 workflow，把天气工具包为 activity；openai_agents/basic/run_worker.py:38–69 注册 OpenAIAgentsPlugin，给模型 activity 30 秒 start-to-close timeout，再注册业务 activities。关键片段是：

# temporalio/samples-python，tools_workflow.py:20–24
 tools=[
     temporal_agents.workflow.activity_as_tool(
         get_weather, start_to_close_timeout=timedelta(seconds=10)
     )
 ],

恢复粒度来自 workflow 历史与 activity 完成记录，而不是把整个模型循环重新请求一遍。但如果 activity 已把邮件发出去、尚未来得及上报成功就崩溃，重试仍可能重发；邮件服务的 idempotency key、业务 outbox 或查询已发送回执仍是应用责任。样例证明集成方式，未证明无限期任务已经在生产通过故障注入。

【源码】Raft 自建较轻的数据库机制。packages/server/src/services/durableTasks.ts:10–15,93–135 在业务变更的同一事务内写 task，提交后先 inline 执行；恢复 worker 回收过期 lease，每次写操作以 (claimed_by, attempts) fencing。243–254 使用以下原子认领：

-- durableTasks.ts:243–254，节选核心选择逻辑
WHERE id IN (
  SELECT id FROM ...
  WHERE state = 'open' AND lease_until < ... AND attempts < max_attempts
  ORDER BY lease_until LIMIT ... FOR UPDATE SKIP LOCKED
)

它允许 handler 被执行两次，要求 handler 幂等并用 revision 防止旧任务覆盖新状态（47–48）；不是 Temporal 那种程序历史 replay，且 recovery 开关在 294–306 受环境变量控制，不能凭源文件存在就宣称部署已开启。发送层另有 packages/server/src/services/agentSendReplayService.ts:75–195：onConflictDoNothing 后查回同 sender/key 的消息；若开启严格校验，同 key 不同目标、正文或附件会拒绝，而不是假装新内容已送出。消息、附件和 onInserted 派生 outbox 工作可落在同一事务，是比“消息去重”更完整的边界。

【源码】同属 botiverse 的 OAR 是运行时适配层，不能当成 Raft 所有底层能力已统一。packages/oar/src/runtimes/pi-durable/session.ts:33–77 先 watch snapshot 再订阅增量，调用底层 harness.resume()，按 inputId 查询已有 submission；prompt 在忙时 reject、steer 要求有 active turn、queue 映射 followUp。94–113 明确暴露 durable queue、撤回、abort 和带 cursor 的 rawEvents。durability 的责任实际在所接的 pi-durable；其他 adapter 是否同等强，需要逐个看 capability。

OpenHands SDK 的 openhands-sdk/openhands/sdk/conversation/event_store.py:188–238 给出事件日志层的具体保证：跨进程文件锁内先从磁盘同步，拒绝重复 event ID 与不存在的 parent ID，分配连续 index，写盘后才更新内存映射。它支持重建有序会话，但“重复 append 报错”与“重复发送安全返回同一 receipt”并不等价。Goose 上述 scheduler 的 clear_running_state 会清掉 currently_running、session ID 和进程启动时间；其 JSON 调度清单不是模型步骤的事务日志。比较可靠性时应分别看调度计划、推理事件、外部副作用与客户端同步，而不以有无一个数据库作判断。

【判断】应要求厂商演示三种崩溃点：模型返回后尚未保存、外部动作成功但 receipt 未落盘、用户取消与恢复同时发生。聊天记录能重载只覆盖第一层状态；事务/outbox/fencing 把业务正确性补齐；durable engine 降低长流程编排成本。对投资而言，“可恢复”必须问清恢复哪个层级、最长重复窗口和谁承担副作用补偿。

4. 说话机制：把“模型完成”与“向人发送”变成两个事件

【讲座】Grok Bot 只有调用 SendToUser 才对外说话，普通模型文字留在内部；允许完成工作但沉默。工具承载文本、文件、选择题、密码输入和付款确认；最后一次发送还能结束 turn，省掉一次只为总结的模型调用。这样，通知频率成为可训练、可评测的决策，而非每次唤醒必回一句。（讲座：lecture-slides.md:106–116。）

【源码】Letta/MemGPT 的历史 API server 早已采用显式发送：archive 的 letta/functions/function_sets/base.py:71–84 中 send_message 调用 interface.assistant_message，与内存工具相分离。必须标明这是归档实现，不能据此推断当前 Letta Code 所有输出都经同一个工具。Hermes Bot Mode 则提供另一种兼容路线：tui_gateway/prompt_turn.py:19–28 保留消息记录与 completion event，只把成功 turn 的纯沉默标记变为空文本；失败时保留诊断。因此它仍可依赖 final response，却在 delivery boundary 决定不展示。OpenClaw heartbeat 的当前约定也是 NO_REPLY（docs/gateway/heartbeat.md:98），并非所有场景都使用 Grok 式唯一发送工具。

DS Bot 的 ds-bot/src/host/prompt.js:8–16 按来源决定 final text 投给谁：来自其他 Bot 的请求自动回送请求者，reply_to: user 则出现在接收 Bot 自己的用户聊天；群组使用独立 conversation。它要求 ask_user 发出选择卡后结束 turn，避免阻塞式提问让其他 Bot 消息排在后面。这个约定能在源码中读到，但 prompt 要求本身不等于每个模型都会遵守，需 delivery 层一起验证。

【官方】Muse 的设计文把值得打扰才通知、可调主动程度、结构化接受/拒绝卡和可交互 Artifacts 分别处理；其中审批不能仅靠主 agent 理解一句“好”。Claude Channels 文档也区分 terminal 中的工具发送确认与目标平台真正收到的正文。ChatGPT agent 的发布说明允许用户接管浏览器并在需要时确认；这些 UI 行为不能证明后端采用某个私有 send 工具。

【判断】至少应记录内部事件、投递尝试和用户可见消息三份状态。“不说话”要成为明确成功结果，否则监控会把沉默当失败重试，最终造成通知风暴。审批卡还应绑定动作版本：用户批准的收件人、正文、金额若随后改变，原批准就不应继续有效。

5. 工具加载：稳定工具目录与按需 schema 可以共存

【讲座】Grok Bot 先给名称，需要时加载详细定义；单工具 description＋schema 控制在 4,000 字符内，回合之间不要任意增删工具，失效时返回可操作错误。这里不是“工具越少越好”，而是把发现、定义暴露和调用授权分开：一个能力可以已登记、尚未把长 schema 放入模型输入，同时此刻没有调用权限。（讲座：lecture-slides.md:118、135–139。）

【源码】Codex 的 codex-rs/core/src/tools/handlers/tool_search.rs:66–119 仅将 exposure.is_deferred() 的 registry entry 加入搜索；稳定 runtime 用弱引用身份判断，动态条目比较 search info，再决定是否重建搜索 handler。232–282 校验 query/limit 并返回选中的定义；289–335 在 code mode 中先检查当前 step 的嵌套工具策略，再限制返回数量，还传入 tool_input_schema_max_bytes 与 description-first 配置。这个先过滤权限再取 top-k 的顺序很关键，否则搜索前几名全是不可调用工具，会制造“搜到了但用不了”的死循环。不能把 Grok 的 4,000 字符建议当成 Codex 的硬编码全局上限。

Goose 的 crates/goose/src/agents/platform_extensions/ext_manager.rs:68–129 把 search_available_extensions 和 manage_extensions 做成工具：先发现 extension，再启用/停用，资源另用 list/read。它改变的是 extension 状态，不等同于 Codex 从既有 deferred registry 检索 schema；工具集合变化带来的 prefix 成本需要另测。Goose 同时在 crates/goose/src/agents/platform_extensions/code_execution.rs:608 提示先用 bash 搜索、读取签名与输入输出类型，再运行 TypeScript，是把大量接口移出模型初始输入、交由代码环境发现的另一条路。

DeepSeek Harness 的 packages/skill/tool-skill/src/index.ts:28–84 将 skill catalog 描述默认限制为 500 字符，持久记录此次发布的 entries，按需调用 skill 获取完整说明，并使 catalog 可见性匹配当前 agent 实际能解析到的 tool registration。这是 skill 加载，不宜冒充所有 MCP 工具都做了语义搜索。Claude Agent SDK 公开了 allowed tools、hooks、skills 等宿主接口，但核心 CLI 是单独 subprocess：src/claude_agent_sdk/_internal/transport/subprocess_cli.py:36–68 甚至处理宿主退出后的子进程清理；SDK 源码不是完整 Claude Code 模型调度器。

【官方】Manus 2025-07-18 工程文走“保留定义、限制选择”的路线：由状态决定允许的动作，避免删除 schema 破坏 cache 和旧工具引用。它描述了 prefill/logit masking；这是当时的工程自述，不能未经证据转成“Cue 2026 仍完全相同”。

【判断】工具数量必须同时报“安装数、当前可见数、首次请求 schema tokens、搜索召回率”。四千个连接应用不意味着一次请求有四千个工具 schema。对于开发者，优先固定 catalog 与序列化，再决定用 tool search、代码接口文件还是模型端约束；否则一次小小的插件热更新就可能把整段缓存打掉。

6. 计算机使用：表示法、执行权与人接管各有一层

【讲座】Grok 把 computer use 交给独立 helper，优先读页面结构，必要时在 1280×800 像素屏上点击；登录、验证码、captcha、支付交人。主 agent 保持 API→搜索→已登录浏览器→桌面的成本次序，且连接器坏了不能擅自从浏览器绕过去。屏幕放 helper 不只是节省 token，也缩小网页注入进入主对话的面积。（讲座：lecture-slides.md:120–128。）

【源码】OpenHands SDK 的 openhands-tools/openhands/tools/browser_use/impl.py:553–585 以节点 index 点击，get_state(include_screenshot=False) 默认取结构；需要截图时拆出 screenshot 数据单独返回。它证明结构操作与图片可以混合，而不能证明任何网页上的 index 永久有效；页面变化后必须刷新状态。Raft 的 packages/computer/src/browserHandoff.ts:19–56 只是验证 http(s) URL 后调用系统浏览器 opener，在 Windows 避免经 cmd.exe；这个名称含 handoff 的文件并不是“人接管远程 agent 浏览器”的实现，不能用关键词命中充证据。

E2B 的 packages/desktop-js/src/sandbox.ts:267–299 是更底层的像素工具：截图实际执行 scrot --pointer，通过文件 API 读临时 PNG，清理失败不阻止返回；点击通过 xdotool click 1，双击是 --repeat 2 1。这些函数没有自行识别按钮、判断是否已点击成功或选择何时交给人。开发者仍需在上层实现观察—动作—再观察与授权状态机；“提供 desktop SDK”不等于“提供完整电脑 agent”。

【官方】Muse 的安全文给出更严格的 browser helper：CDP broker 在 runtime cell 外，helper 只看 accessibility tree，不拿原始 DOM、不执行页面 JavaScript；用户接管或安全填充密码时 agent 暂停。ChatGPT agent 官方材料则组合视觉浏览器、文本浏览器、terminal 与 connectors，用户可随时接管。这些都是厂商说明，本次没有独立验证 broker 能否被绕过，也没有证据把两者归为同一 computer-use 模型。

【判断】DOM 更丰富但扩大泄漏与脚本执行面；accessibility tree 更紧凑却丢失部分视觉布局；像素通用但慢且易受尺寸变化影响。能访问页面不代表能安全处理凭据，能点击不代表能恢复中断交易。采购或投研应把任务覆盖率、人接管率、失败恢复及每一步可审计性一起看，而不是只比较点击速度。

7. 多 agent：上下文隔离之后还要定义消息和取消语义

【讲座】Grok Bot 的主 agent 快速回应，长研究、视频、电脑操作、云端 coding 分给 fresh-context helpers；主 agent 持续接用户纠偏，用 todo 跟踪请求，可以查看或给 helper 发消息。收益是把长工具轨迹移出主上下文，但共享电脑、文件和记忆随即成为并发系统问题。（讲座：lecture-slides.md:41–42、130–133。）

【源码】Codex 并不是所有 helper 都一律空白上下文。codex-rs/core/src/agent/control/spawn.rs:81–124 明确筛选 fork 继承内容，保留 system/developer/user 和部分回答，排除工具调用、reasoning、旧 inter-agent communication 与父级累计用量；full-history fork 还可以保留上下文 baseline。codex-rs/core/src/agent/control/mailbox.rs:15–55,59–92 用 ThreadId→Mailbox 保存队列，watch 通知有待收信，recipient 卸载时仍保留消息。但这里的结构是内存 Mutex<HashMap<...>>，单看这个文件不能把 residency 卸载不丢信扩大成进程崩溃后保证投递。

Hermes 则要区分短期 delegate 与 Bot Mode 的长期同事。tools/delegate_tool_child_run.py:64–83 在注册 child 时检查 parent 是否已停止，把晚创建 child 也取消，补上“停止已发出，但 fan-out 尚未创建完”的竞态；42–46 记录未赶在 child 停止前送达的 steer。Bot Mode 的 tools/bot_mode_dm.py:1–13,67–95 将 message_agent 限在 canonical Bot Chat，验证实时 roster，由服务端加来源，后台进程通过本地 CLI 或 peer gateway 投递，完成通知再唤醒发送者。返回 queued + delivery_id 只是提交确认，不是收件回执；工具说明还将消息上限设为 16,000 字符（41–46），防止同事把整段上下文灌过来。

DS Bot 的 ds-bot/src/host/tools.js:61–85 拒绝向自己发送，解析 Bot 身份再走异步 deliver；ds-bot/src/host/prompt.js:23–32 给 Main Bot 建人、分工、组群权限，普通 Bot 不自动拥有同等管理权。Claude Agent SDK 的 src/claude_agent_sdk/types.py:2557–2566 默认只向宿主转发 subagent 的 tool-use/result，带 parent_tool_use_id，可选择开启文本/thinking 转发。这种流量分层能让 UI 显示进度而不把嵌套轨迹全部交回主模型。Raft/OAR 则提供跨 harness 的统一控制/观察接口；具体 agent 各自保留什么 context，仍由相应 adapter 与 runtime 决定。

【官方】Muse 公开了 browser subagent；dots 发布文把“未来的 dots 团队”与现在一个 primary dot 区分，不能从未来叙事推出已发布任意规模同事网络。Manus/Cue 的产品页称每个 agent 有自己的邮箱、电话、钱包和电脑，群聊里可以互相分工；更可核验的是 Agents API：每个 agent 的 task_id 指向持久主会话，默认 IM agent 可通过 agent-default-main_task 调用 task.sendMessage，不必先查 UUID。这给出了身份与对话的映射，仍没有公开 mailbox 顺序、共享记忆锁或取消传播的完整协议。

【判断】并行度不是协调能力。值得测的是任务归属是否唯一、helper 结果是否过期、取消能否覆盖晚出生的 child、同一浏览器是否有互斥控制权。给投资对象一个能被中途修改的任务，比看它一次生成十个 agent 更能揭示技术水平。

8. 上下文工程：把缓存稳定性当作运行时不变量

【讲座】Grok 在两次摘要之间固定 tools、system prompt（含 memory/routine 快照）、首条消息；新时间与变更说明追加末尾。工具排序稳定、分段 hash 定位 cache miss，打开聊天或输入时预热。超过 100K tokens 的大 turn 结束约十分钟后，趁 cache 温热异步摘要，保留最近若干消息原文；截图和大工具结果分别留给 helper 与文件。这些阈值均来自讲座，不是跨产品推荐默认值。（讲座：lecture-slides.md:148–165。）

【源码】Hermes 的 gateway/session_prompt_pin.py:46–81 持久化 effective prompt 输入，读写带 expected_session_id fence；先写盘再发布内存 entry，旧 turn 不能把旧 prompt pin 写进 reset/resume 后的新 session。这把缓存问题与并发正确性连在一起。DS Bot 的 ds-bot/src/host/prompt.js:1–8,38–49 故意不把动态 roster 放进身份前缀，让模型需要时 list_bots；ds-bot/src/host/memory.js:19–22 说明每个 Session 初次渲染冻结 memory section，到 checkpoint 或 fresh part 才重取。代价是长期记忆写入成功与当前上下文看见更新之间存在延迟，系统必须另有查询或追加提示。

Goose 的 crates/goose/src/agents/state_machine/ops_compaction.rs:257–273 只在下一次 inference 之前且超过阈值时压缩；若 assistant 尾部结束 turn、仍等待 tool responses 或已有成功 final-output tool，则跳过。原因不是保守，而是压掉未回答的 tool request 会让随后 result 成为孤儿。308–328 将压缩结果和 usage 作为状态机 effect 提交。它与 Grok 的“用户离开后暖缓存摘要”是两种时机：前者守模型调用边界，后者优化交互等待和缓存费用。

Codex fork 的 durable baseline 复用已经体现 prefix 价值；DSH 的 skill catalog 另保留结构化 source entries，让 UI/持久化消费者不用从面向模型的 XML 风格文案反向解析事实。Manus 工程文强调 append-only、稳定序列化、保留可恢复的 URL/文件路径，并把失败记录留在上下文；以上是 2025 年经验，不是本次独立测得的 cache 命中率。

【判断】应同时观测 prefix hash、cached/uncached input、摘要成本和摘要后任务正确率。缓存命中不是目的本身：省掉几千 token 却丢失用户刚撤回的授权，属于错误。稳定的是已发布的历史，变化通过明确事件追加；压缩是创建新上下文版本，应保留未完成任务、权限、来源、关键路径与最新纠正的原文锚点。

9. 记忆与 skills：写得进去还不够，要知道谁可改、何时读

【讲座】Grok profile 最多 100 facts/4,000 字符常驻，log 取 30 条相关近期事实，短 notes 更快衰减，其余走搜索；重要性加权、时间衰减，每 turn 后增改，删除只能针对本次看见的事实。关于用户的事实跨 agent 共享、每 agent 写自己的文件；memory 是信息，不是指令。skills 为 skills/*/SKILL.md，先提供指针，匹配任务再加载正文。（讲座：lecture-slides.md:48–53、167–174。）

【源码】Letta 必须分代看：letta-ai/letta 当前 README:5,39–41 已将活跃实现指向 letta-code，原 API server 在 archive。归档 letta/schemas/memory.py:155–192 把 block 的字符限额、只读标记与内容格式化进上下文；letta/functions/function_sets/base.py:87–164 提供 conversation search 与 archival insert，246–280 让模型追加/精确替换 core block，替换找不到旧文本就报错，以空字符串替换可删除。MemGPT 的核心是有限的工作记忆加显式检索/编辑通道，不是简单把全聊天做 embedding。

当前 Letta Code 的 src/memory-constraints.ts:11–33,39–73,101–127 已把约束落在 memory 文件树：支持 core/file 字符预算、目录深度、shared-memory 布局与只读 glob；MemFS v2 要求每层必要的 MEMORY.md 索引；检查只读文件时比较 trusted accepted tree，创建、修改、删除都拒绝。这个服务级约束比提示模型“别改这些记忆”强，也显示 block 路线可以演进为受治理的文件系统，并非两者永远对立。

Hermes 的 tools/memory_tool.py:1–5,48–57 将 MEMORY.md 与 USER.md 分开，配置缺省限额分别 2,200 和 1,375 字符；171–210 对后台 review 删除/替换设置 gate，可进入 pending 等人工处理。与 Grok 自动删“已经看到的事实”相比，它在后台遗忘上更谨慎。tools/skills_tool.py:1–4,206–239 则扫描 YAML frontmatter，先给 name/description，skill_view 才读正文，平台/环境条件还影响可见性。

Codex 是批处理记忆管线：codex-rs/memories/README.md:29–75 描述仅符合条件的 root session 启动时后台提取旧 rollout，按 age/idle window、租约和并发上限筛选；phase 1 产出 raw memory 与 rollout summary 并去除 secrets。实际 phase 2 的 codex-rs/memories/write/src/phase2.rs:49–145 先拿全局锁、建立 git baseline、加载有数量与未使用天数约束的输入，再运行受限 consolidation agent。README:85–137 进一步说明按 usage count/last usage 排序，落为 raw_memories.md、rollout_summaries/，由 git diff 暴露删除与新增，工作区无变化就跳过。它的“衰减”至少包含基于近期使用的筛选，不应写成 Grok 同款 relevance×time 公式。

DS Bot 提供更小而直观的实现：ds-bot/src/host/memory.js:1–22,32–68 有每 Bot、team 共享目录、逐条 before/after journal、session 快照、deleted-Bot archive 和 reviewed cursor；单事实 300 字符、主索引 4,000、topic 16,000、最多 40 topics。remember/forget 与 turn 后 review 共用写入路径，单进程串行写，固定快照保护 cache。它适合解释一个产品如何从“记住偏好”落到有归属和版本的存储，但串行化只在持有 team 的进程内，不能据此宣称多机一致性已解决。

【判断】长期护城河不是记忆条数，而是事实可追溯、可纠正、可遗忘且不跨域串用。SKILL.md 的名称、描述、正文、可选 scripts/references 正在收敛成懒加载知识接口；skills 可以含操作指令，因此必须按其可信来源处理，不能借“记忆共享”把某个网页上的命令升级成所有 agent 的全局规则。

10. 安全：模型判断与不可绕过的执行边界要同时存在

【讲座】Grok 用独立 reviewer 检查风险动作；被挡后请求用户确认，15 秒无回应仍阻止。email/webhook 标为不可信，记忆只提供事实；未经要求不替用户联系别人，新增 routines 要批准；密码经安全输入进入环境变量，操作用户电脑需授权。这里的 15 秒是讲座行为，不能推广成行业默认，更不能把超时当批准。（讲座：lecture-slides.md:141–145。）

【源码】Codex 的 codex-rs/core/src/guardian/mod.rs:1–3,79–101 将 issuing step 的审核上下文与隔离 reviewer 分开；codex-rs/core/src/guardian/approval_request.rs:13–73 为 exec、stdin、patch、network、MCP 与权限扩张建立不同 typed request。MCP 请求不仅带 tool name 和 arguments，也带 connector、已连接账号、description、风险 annotations；网络请求含目标 host/protocol/port。这样 reviewer 能判断“替哪个账号执行哪种动作”，而非只读一行主 agent 自述。代码证明审核输入结构与独立路径存在，不证明审核误放率。

Claude SDK 的 src/claude_agent_sdk/types.py:2502–2523 是容易被忽略的边界：can_use_tool 不是每次调用必经的总闸，已被 permission rules 或 bypass 模式允许的动作可跳过它；要观察/拦截每次调用应使用 PreToolUse hook，而返回 allow 的 hook 又会绕过该 callback。2572–2596 的 verbatim_prompts 防止外部拼接文本中的 @path 被 CLI 当成本地文件展开，并有最低 CLI 版本要求；2675–2678 明说 skills 选择只是 context filter，agent 仍可能用文件工具读到没列出的 skill。公开 claude-code 仓库里的 Hookify 插件提供具体例子：plugins/hookify/hooks/hooks.json:4–14 注册十秒 timeout 的 PreToolUse 命令，plugins/hookify/hooks/pretooluse.py:25–70 加载本地规则、输出判断，但 import/执行异常时返回错误说明并放行。它是可扩展的策略插件，不能当成不可绕过且失败关闭的安全内核。提示可见性、工具权限与文件权限不能混成一个开关。

【源码】agent-vault 展示了“凭据不进模型”与“凭据不可被 agent 读出”的差距。src/vault.ts:31–40,47–74 用 AES-256-GCM，key 和密文都放本地目录，以 0700/0600 保护；113–118 可读取 key 解密。CLI 支持脱敏占位符、恢复文件内容与仅列 key 名；src/cli.ts:109–123 恢复后把真实 secret 写入目标文件。它减少日志和对话意外泄漏，却不能隔离拥有同一 OS 用户任意 shell/read 权限的 agent。不要因同属 botiverse 就断言 Raft 所有凭据已经过此工具，更不能把 TTY 检查视为硬安全边界。

【官方】Muse 提供另一种更强的结构：authd 保存真实凭据，privsep worker 执行连接器，Sentinel 审批后在网络边界用真 token 替换 surrogate；审批答复由 UI 直接回 Sentinel，不经主聊天。其 tainted egress 用内核数据流标记限制读取用户数据后的自动外发。以上均来自Meta 安全文，不是我们复现的隔离保证。dots 的安全 FAQ区分连接范围、Custom Rules、auto-review；Auto-review 研究文强调检查可能造成严重或难逆损害的动作。开放的 Codex Guardian 不能直接充当闭源 dots 整套安全实现的代码证明。

Sierra 的 Personal Agent Protocol 公告（2026-10-06）处理 agent 与企业之间的身份授权：网站发现能力，guest session 可先查询，需要账号时 OAuth 授权，session 跨网站/API/企业 agent 延续，消费者决定读写权限，企业决定开放操作。它不是新的本地 sandbox，也不是多 agent 调度器。尤其公告说 v0.1 规范计划当月稍后发布，细权限、push 与支付扩展是后续方向；截至本次材料，不能把它写成已有成熟公开实现和确定字段的协议。

【判断】投资上最有区分度的是权限绑定的粒度与可撤销性：谁代表谁、动作带走什么数据、批准是否绑定最终参数、被拒后能否换工具绕行。reviewer 降低人工负担，OS/网络/凭据隔离限制最坏结果，两者互补。单纯 prompt 标注 untrusted 是必要但不充分的防线。

11. 评测与训练闭环：用失败轨迹验证整个系统

【讲座】Grok 的内环每天把失败转 eval，调整 harness/prompt/inference 后回归；外环每几个月将 harness 与 evals 用于下代模型训练。SFT 学工具格式和快答时机，RL 练长指令、skills/memory、点击 grounding 和多 Bot 协作；主 agent 与长任务 helper 的优化目标不同。这是路线自述，讲座没有给可复现数据集、训练配方或独立指标。（讲座：lecture-slides.md:176–186。）

【源码】开源最硬的证据首先是失败语义测试。Raft packages/server/src/services/durableTasks.test.ts:46–80 真实检验事务回滚不留 task、lease 过期只被一个 worker 认领、旧 inline writer 返回 fenced；83–135 覆盖重试耗尽与不认识的 task kind。Hermes tests/cron/test_restart_safe_worker_death_evidence.py:11–48,58–82 参数化 hard exit、payload exception、并发 recovery、timeout，并让真实子进程 os._exit(9)，再观察账本和失败可见性。这比只断言“有 heartbeat 函数”更贴近 always-on 风险。本文只检查测试源码，没有在这些大型项目上安装依赖、运行整套测试，因此不声称测试在本机通过。

DeepSeek Harness 的 snapshots/session/skill-load/snapshot.yml:1–12 将 scenario、headless profile、composition、prompt/schema 来源以及 workspace setup 固定；同目录保存版本化 session JSONL。recording: authored 明确是编写的样例，不应包装成生产成功轨迹。它可测序列化和 harness 契约回归，但无法单独证明模型在陌生任务上正确使用 skill。Codex 的 Guardian UI snapshots、memory pipeline 测试以及 OpenHands 的事件存储测试也属于工程回归，和强化学习收益证据不是同一层。

【官方】OpenAI 的 GPT-6 Astra system card 的 dots 附录描述用去标识的员工 dots rollout 构造审核测试，再定向修改成不应执行的动作，观察原始请求的拒绝率和合成违规动作的召回率。这说明“更少打扰”与“更多阻止越权”应在同一曲线上评估；它仍是厂商自评，合成负例也不覆盖真实长期漂移。Meta 安全文披露 agentic red-teaming 与外部赏金计划，但未提供可直接与 Grok/OpenClaw 对齐的长期成功率。Manus 的 context engineering 路线则把快速改 harness 与底层模型升级解耦，和模型厂商纵向训练主 agent/helper 的路线存在明确分叉。

【独立证据】AP 对 Muse 的报道（2026-09-08）与 Axios 对 dots 发布会的报道（2026-09-29）能核实产品发布与公开演示，后者记录了现场延迟；它们不能核实快照、幂等或注入拦截率。本次未找到足以横向排名所有对象的独立 always-on 长期评测，故不造“综合可靠性第一”。

【判断】Charles 若做产品，最小有用 eval 应是一条跨机制轨迹：重复事件到达→执行到外部副作用→杀进程→恢复→用户改目标→helper 晚回→摘要→下周召回旧偏好。分别判定任务是否成功、重复副作用数、越权数、纠偏延迟、无效通知、可恢复事实和总成本。若做投资，优先看团队能否把真实事故变成这种回归资产，并展示随版本改善的曲线；模型成本下降会普惠行业，长期授权、恢复语义和可验证反馈循环的积累更难复制。
